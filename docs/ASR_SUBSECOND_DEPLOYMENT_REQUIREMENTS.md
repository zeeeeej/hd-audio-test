# ASR 1 秒响应部署配置与验收指标

## 1. 目标定义

本文中的“ASR 1 秒内响应”定义为：

> 用户结束说话或点击停止录音后，浏览器在 1 秒内收到并展示最终识别文字。

该指标是端到端最终结果延迟，不只是模型输出第一个文字 token 的时间，也不包含用户实际说话所花的时间。

需要分别统计两种交互方式：

- 手动停止：从用户点击“停止录音”到页面展示最终文字。
- 自动断句：从最后一个有效语音采样点到页面展示最终文字，其中包含 VAD 静音检测时间。

流式识别时还需要统计中间结果延迟：用户说话过程中，页面应持续显示临时识别文字，但临时文字允许在后续音频到达后被修正。

## 2. 推荐硬件配置

以下配置以模型常驻显存、BF16、vLLM、CUDA Graph、单卡部署为前提。官方没有公布延迟测试所使用 GPU 的准确型号，因此下表是为 1 秒端到端目标预留余量后的工程配置，最终必须以目标服务器压测结果验收。

| 模型与并发 | GPU | CPU / 内存 | 使用定位 |
| --- | --- | --- | --- |
| Qwen3-ASR-0.6B，1～2 并发 | NVIDIA L4 24GB | 8～16 核 / 32GB | 最低成本推荐方案 |
| Qwen3-ASR-0.6B，3～8 并发 | NVIDIA L40S 48GB | 16～24 核 / 64GB | 稳定低延迟方案 |
| Qwen3-ASR-1.7B，1～2 并发 | NVIDIA L4 24GB | 16 核 / 64GB | 1.7B 最低推荐方案 |
| Qwen3-ASR-1.7B，3～8 并发 | NVIDIA L40S 48GB | 24 核 / 64～128GB | 1.7B 稳定方案 |
| Qwen3-ASR-1.7B，8～16 并发 | NVIDIA H100 80GB，或 2×L40S 48GB | 32 核 / 128GB | 高并发方案 |
| 严格生产 SLA | 两台相同规格服务器 | 负载均衡、健康检查 | 避免单机故障和排队造成超时 |

通用配置建议：

- NVMe SSD：500GB 以上。
- 网络：千兆以上，业务服务器与 Voice 服务器优先部署在同一内网。
- 操作系统：Ubuntu 22.04 或 24.04。
- 推理精度：BF16。
- 推理后端：vLLM。
- 启用 CUDA Graph；长音频或批处理可启用 FlashAttention 2。
- 模型启动时加载并常驻显存，禁止请求到达后才加载模型。
- 服务启动后自动执行 3～5 次预热识别。
- 严格 1 秒 SLA 时，ASR 不与 TTS、YOLO 等其他模型共享 GPU。

## 3. 推荐选型结论

### 3.1 最低成本方案

```text
Qwen3-ASR-0.6B
NVIDIA L4 24GB
8～16 核 CPU
32GB 内存
500GB NVMe SSD
最多 1～2 个并发识别请求
```

该方案适合饮料名称、点单指令等短语音识别。0.6B 模型的速度和成本更低，业务专有名称通过热词、纠错词典和微调补充。

### 3.2 1.7B 推荐方案

```text
Qwen3-ASR-1.7B
NVIDIA L4 24GB
16 核 CPU
64GB 内存
500GB NVMe SSD
最多 1～2 个并发识别请求
```

当环境噪声、口音、方言或者复杂表达较多时，可以使用 1.7B。若需要 3～8 个并发请求仍保持稳定的 1 秒延迟目标，建议使用 L40S 48GB。

若识别目标主要是较短的饮料名称，优先使用 0.6B 加业务热词或微调，通常比直接升级 1.7B 更节省部署成本。

## 4. 必须采用流式上传和流式识别

一次性上传完整录音的流程是：

```text
用户说完
  → 浏览器封装完整 WebM/WAV 文件
  → 上传业务服务器
  → 业务服务器转发完整文件
  → Voice 服务器解码完整文件
  → GPU 开始识别
  → 返回最终文字
```

录音封装、两次网络传输和音频解码都发生在用户停止说话之后，容易使端到端延迟超过 1 秒。

目标流程应调整为：

```text
用户开始说话
  → 浏览器每 100～250ms 发送一块 16kHz 单声道 PCM
  → 业务服务器通过长连接转发
  → Voice 服务器持续执行流式识别
  → 页面持续显示临时文字
用户结束说话
  → Voice 服务器完成最后一块音频和最终修正
  → 立即返回最终文字
```

实现要求：

- 浏览器与业务服务器使用 WebSocket 长连接。
- 业务服务器与 Voice 服务器使用 WebSocket 或 gRPC 双向流。
- 音频格式优先使用 16kHz、16-bit、单声道 PCM，避免结束录音后再转码。
- 每个音频块建议为 100～250ms；不建议等待整句录音完成。
- Qwen3-ASR 流式推理使用 vLLM 后端。官方当前说明 Transformers 后端不提供流式推理。
- 已知业务为中文时直接指定 `language="Chinese"`，减少自动语言判断带来的不确定性。
- 点单短句应限制 `max_new_tokens`，不使用为长音频准备的超大生成上限。
- 不需要时间戳时不要加载 ForcedAligner，避免额外显存和延迟。
- 使用 VAD 自动结束时，静音判定窗口建议从 300～500ms 起压测。

## 5. 官方效率数据的正确理解

Qwen3-ASR 技术报告采用 vLLM、CUDA Graph 和 BF16 测试约 2 分钟的音频，报告中的部分在线异步数据如下：

| 模型 | 并发 | TTFT 平均值 | TTFT P95 | 在线 RTF |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-ASR-0.6B | 1 | 92ms | 105ms | 0.00940 |
| Qwen3-ASR-0.6B | 8 | 228ms | 417ms | 0.01472 |
| Qwen3-ASR-0.6B | 16 | 459ms | 882ms | 0.01936 |
| Qwen3-ASR-1.7B | 1 | 102ms | 113ms | 0.01483 |
| Qwen3-ASR-1.7B | 8 | 224ms | 382ms | 0.02000 |
| Qwen3-ASR-1.7B | 16 | 443ms | 791ms | 0.02640 |

这些数字不能直接当作本项目的最终延迟保证，原因包括：

1. TTFT 只表示第一个文字 token 的时间，不是完整文字返回时间。
2. 官方报告没有说明测试所用 GPU 的准确型号。
3. 官方数据不包含浏览器、业务服务器、音频传输、VAD 和页面渲染时间。
4. 热词数量、输出长度、音频噪声和并发排队都会影响最终延迟。

RTF 是识别计算耗时与音频时长的比值。例如 RTF 为 0.1，代表识别 10 秒音频约需要 1 秒计算。为了给网络、VAD 和页面展示留下余量，本项目要求短语音识别 RTF P99 小于 0.1。

## 6. 一秒响应验收标准

建议正式验收基线如下：

```text
模型：Qwen3-ASR-0.6B 或 Qwen3-ASR-1.7B
语言：Chinese，避免自动语言检测
音频：16kHz、16-bit、单声道 PCM
单条语音：不超过 10 秒
文本长度：不超过 50 个中文字符
并发：按采购规格限定
模型状态：已加载、已完成预热
手动停止到最终文字 TTFA P95：小于 800ms
手动停止到最终文字 TTFA P99：小于 1000ms
自动断句到最终文字 P99：小于 1000ms，包含 VAD 静音检测
流式中间文字更新间隔 P95：小于 500ms
识别 RTF P99：小于 0.1
服务错误率：小于 0.1%
压测时长：连续 30 分钟以上
```

这里沿用 `TTFA` 表示最终文字可用时间（Time To Final ASR Result），避免把它与官方报告中的首 token 指标 `TTFT` 混淆。

端到端计时范围必须覆盖：

```text
最后一个有效语音采样点或点击停止
  → 浏览器发送最后一块音频
  → 业务服务器转发
  → Voice 服务器完成最终识别
  → 业务服务器返回结果
  → 浏览器展示最终文字
```

## 7. 必须记录的监控指标

- `asr_audio_duration_ms`：本次语音长度。
- `asr_upload_tail_ms`：结束说话后最后一块音频上传耗时。
- `asr_queue_ms`：请求在 Voice 服务器中的排队时间。
- `asr_first_token_ms`：模型首个文字 token 时间。
- `asr_final_result_ms`：Voice 服务器产生最终文字的时间。
- `asr_browser_display_ms`：浏览器展示最终文字的端到端时间。
- `asr_vad_endpoint_ms`：VAD 判断用户结束说话的时间。
- `asr_rtf`：识别计算耗时与音频时长之比。
- `asr_hotword_exact_match`：业务热词完全正确识别比例。
- GPU 利用率、显存峰值、CPU 利用率和网络传输时间。

需要分别统计平均值、P50、P95 和 P99，不能只看单次测试或平均值。

## 8. 识别质量验收

速度达标不能替代识别准确率验收。建议准备独立业务测试集，包括：

- 每个饮料名称至少由不同性别、年龄、口音的人员录制。
- 包含安静环境、商场背景声、设备风扇声和远距离说话。
- 包含“来一瓶东方树叶”“我要东方树叶茉莉花茶”等真实句式。
- 新增饮料名称不能只出现在训练集，也必须放入独立测试集。

建议业务验收目标：

```text
安静环境饮料名称完全正确率：不低于 98%
目标噪声环境饮料名称完全正确率：不低于 95%
热词误替换率：低于 1%
无语音输入误识别率：低于 0.5%
```

以上是建议的业务目标，不是 Qwen 官方承诺值，应根据实际录音设备和现场噪声调整。

## 9. 保证 SLA 的服务约束

1. 模型必须常驻显存，不允许请求触发冷启动。
2. 服务必须设置最大并发量，超出容量后限流或转移到其他实例。
3. 请求队列等待时间应限制在 100ms 以内。
4. 浏览器、业务服务器和 Voice 服务器之间使用长连接。
5. 自动断句的 VAD 静音窗口不能超过端到端延迟预算。
6. 业务热词列表在请求前准备好，不能在识别过程中访问外部数据库。
7. 生产环境至少两个实例，通过负载均衡和健康检查实现故障切换。
8. 新模型、新热词、新录音设备或新部署版本上线前，都必须重新执行准确率和延迟压测。

## 10. 最终建议

- 0.6B、1～2 并发、最低成本：选择 **L4 24GB**。
- 0.6B、3～8 并发：选择 **L40S 48GB**。
- 1.7B、1～2 并发：选择 **L4 24GB**。
- 1.7B、3～8 并发：选择 **L40S 48GB**。
- 1.7B、8～16 并发：选择 **H100 80GB** 或 **2×L40S 48GB**。
- 饮料名称等短语音业务优先使用 **0.6B + 热词/微调**，在准确率不达标时再升级 1.7B。
- 无论使用哪种 GPU，都必须采用流式上传、vLLM 流式识别和合理的 VAD 参数，才能稳定达到“结束说话后 1 秒内返回最终文字”。
