# TTS 1 秒响应部署配置与验收指标

## 1. 目标定义

本文中的“TTS 1 秒内响应”定义为：

> 业务服务器提交文字后，浏览器在 1 秒内收到并开始播放第一段有效音频。

该指标是首音频延迟（Time To First Audio，TTFA），不是整段音频生成耗时。

- 可以保证：在规定文本长度、并发量和模型已预热的条件下，第一段声音在 1 秒内开始播放。
- 无法保证：任意长度的整段音频都在 1 秒内生成完毕。
- 对欢迎语、下单成功等固定话术，预生成并缓存音频是最可靠、成本最低的方案。

## 2. 推荐硬件配置

| 模型与并发 | GPU | CPU / 内存 | 使用定位 |
| --- | --- | --- | --- |
| Qwen3-TTS-0.6B，单并发 | NVIDIA L4 24GB | 16 核 / 64GB | 最低成本推荐方案 |
| Qwen3-TTS-0.6B，2～6 并发 | NVIDIA L40S 48GB | 24 核 / 128GB | 稳定低延迟方案 |
| Qwen3-TTS-1.7B，单并发 | NVIDIA L40S 48GB | 16～24 核 / 64～128GB | 1.7B 推荐方案 |
| Qwen3-TTS-1.7B，3～6 并发 | NVIDIA H100 80GB，或 2×L40S 48GB | 32 核 / 128GB | 高并发方案 |
| 严格生产 SLA | 两台相同规格服务器 | 负载均衡、健康检查 | 避免单机故障和排队造成超时 |

通用配置建议：

- NVMe SSD：500GB 以上。
- 网络：千兆以上，业务服务器与 Voice 服务器优先部署在同一内网。
- 操作系统：Ubuntu 22.04 或 24.04。
- 推理精度：BF16。
- 注意力实现：FlashAttention 2。
- 模型启动时加载并常驻显存，禁止收到第一个请求后才加载。
- 服务启动完成后自动执行 3～5 次预热请求。
- TTS GPU 不与 ASR、YOLO 等其他模型共享，避免显存抢占和延迟抖动。

## 3. 推荐选型结论

### 3.1 最低成本方案

```text
Qwen3-TTS-12Hz-0.6B-CustomVoice
NVIDIA L4 24GB
16 核 CPU
64GB 内存
500GB NVMe SSD
单并发
```

该配置适用于业务请求量不高、同一时间只处理一个 TTS 请求的场景。L4 原生支持 BF16，并具备 24GB 显存。

### 3.2 1.7B 推荐方案

```text
Qwen3-TTS-12Hz-1.7B-CustomVoice
NVIDIA L40S 48GB
16～24 核 CPU
64～128GB 内存
500GB～1TB NVMe SSD
单并发或低并发
```

如果需要 3～6 个并发请求仍保持低延迟，使用 H100 80GB，或者部署两个 L40S 实例分担流量。

## 4. 必须采用真正的流式 TTS

当前“按句生成、按句播放”的伪流式流程是：

```text
收到完整句子
  → 生成完整句子音频
  → 保存或组装完整 WAV
  → 返回浏览器
  → 开始播放
```

这个流程必须等待整句生成完成，即使升级 GPU，也不能稳定保证 1 秒内开始播放。

目标流程应调整为：

```text
收到文字
  → 增量生成前 4 个语音 token
  → 解码约 320ms 的音频
  → 立即通过 WebSocket 或 HTTP Chunked 返回
  → 浏览器立即播放
  → 后续音频持续生成、持续发送、持续播放
```

实现要求：

- token 级增量生成，不能等待整句生成完成。
- 流式语音 codec 解码。
- 使用 WebSocket 或 HTTP Chunked 传输音频。
- 浏览器使用 AudioWorklet、Web Audio API 或等价方案连续播放 PCM/Opus 数据。
- 第一包建议包含 200～320ms 的可播放音频。
- 后续音频生成速度必须持续快于播放速度，避免播放中断。

Qwen3-TTS 技术报告说明，12Hz tokenizer 的 4 个 token 对应约 320ms 音频。报告中的第一包延迟结果为：

| 模型 | 并发 | 第一包延迟 | RTF |
| --- | ---: | ---: | ---: |
| Qwen3-TTS-12Hz-0.6B | 1 | 97ms | 0.288 |
| Qwen3-TTS-12Hz-1.7B | 1 | 101ms | 0.313 |
| Qwen3-TTS-12Hz-1.7B | 3 | 195ms | 0.363 |
| Qwen3-TTS-12Hz-1.7B | 6 | 333ms | 0.463 |

注意：官方技术报告没有注明上述延迟测试所用的具体 GPU，因此这些数字用于说明模型具备流式低延迟能力，不能直接作为硬件采购后的 SLA 保证。实际结果必须在目标硬件、目标代码和目标并发下压测。

## 5. 一秒响应验收标准

建议正式验收基线如下：

```text
模型：Qwen3-TTS-12Hz-0.6B-CustomVoice 或 1.7B-CustomVoice
文本：不超过 50 个中文字符
并发：按采购规格限定
模型状态：已加载、已完成预热
第一包：不少于 200ms、不超过 320ms 的有效可播放音频
TTFA P95：小于 800ms
TTFA P99：小于 1000ms
播放连续性：首包播放后无可感知停顿
错误率：小于 0.1%
压测时长：连续 30 分钟以上
```

TTFA 的计时范围必须覆盖完整业务链路：

```text
浏览器发起请求
  → 业务服务器
  → Voice 服务器
  → GPU 生成第一包音频
  → 业务服务器转发
  → 浏览器收到并开始播放
```

同时记录以下指标：

- `tts_queue_ms`：请求排队时间。
- `tts_model_first_token_ms`：模型生成第一个语音 token 的时间。
- `tts_first_audio_chunk_ms`：Voice 服务器生成第一包音频的时间。
- `tts_browser_play_ms`：浏览器真正开始播放的端到端时间。
- `tts_rtf`：生成耗时与生成音频时长之比，必须小于 1。
- GPU 利用率、显存峰值、CPU 利用率和网络传输时间。

## 6. 保证 SLA 的服务约束

硬件本身不能单独保证 1 秒响应，还需要以下约束：

1. 模型常驻显存，不允许请求触发冷启动。
2. 对外设置最大并发量，超出容量后限流、快速失败或转移到其他实例。
3. 请求队列等待时间应限制在 100ms 以内。
4. Voice 服务与业务服务器使用长连接，避免每次重新建立连接。
5. 语音生成期间不能执行模型切换、模型卸载或显存清理。
6. 固定话术优先从内存或对象存储缓存直接返回。
7. 生产环境至少两个实例，通过负载均衡和健康检查实现故障切换。
8. 发布新模型或新推理版本前，必须重新执行延迟和连续播放压测。

## 7. 最终建议

- 0.6B、单并发、最低成本：选择 **L4 24GB**。
- 0.6B、多并发：选择 **L40S 48GB**。
- 1.7B、单并发或低并发：选择 **L40S 48GB**。
- 1.7B、3～6 并发：选择 **H100 80GB** 或 **2×L40S 48GB**。
- 固定业务提示音：提前生成并缓存，可获得最稳定的毫秒级响应。
- 无论采用哪种 GPU，都必须从“按句伪流式”升级为 token/音频块级真正流式，才有条件稳定达到 TTFA P99 小于 1 秒。
